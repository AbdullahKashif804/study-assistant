# Cloudinary replacement safety

Notes, Assignments, Projects, Courses, and Profile updates previously deleted the
old Cloudinary resource before uploading and saving its replacement. Upload or
database failure could leave an existing record pointing to a deleted file.

Those five handlers now share `utils/saveWithFileReplacement.js`:

1. Existing authentication, input validation, and owner-scoped lookup run first.
2. Upload a new resource using the existing folder and upload restrictions.
3. Validate the returned public ID, resource type, and delivery URL; assign the
   same attachment/profile metadata fields and save the document.
4. Only after save resolves, attempt deletion of the old typed resource.
5. If upload or save fails, restore the attachment in the in-memory document and
   attempt deletion of the new resource when its identity is available. The old
   resource is never deleted on this failure path. Re-throw the original error
   so existing controller response handling remains in place.

No-file updates preserve their original save behavior. Notes still invalidate
attachment RAG fields when replacing the file; content-related AI invalidation
remains unchanged. Later population/response failures never trigger compensation
for an already-saved replacement.

Cleanup checks Cloudinary results: `ok` and `not found` are accepted as idempotent
success; other results and exceptions produce a sanitized warning without
overriding the successful update or the original save failure. Provider error
details are suppressed for replacement cleanup. Other utility callers retain
their existing error behavior. Local temporary-file removal runs in finally and
cannot mask a successful remote upload or its original error.

Public IDs are paired with their exact `image`, `raw`, or `video` resource type.
Unknown legacy attachment types are not guessed: deletion is skipped with a
manual-review warning. Legacy profile images may use the existing image-only
fallback. An identical old/new resource identity is never deleted as compensation
or post-save cleanup. Uploads still use Cloudinary's autogenerated public IDs;
no overwrite/public-ID policy changes were introduced.

## Remaining limitations

- Cleanup is best-effort, with no durable queue or automatic retry. A failed old
  deletion leaves an orphan while the new database reference stays valid; failed
  compensation leaves a new orphan while the old reference stays valid. Sanitized
  warnings deliberately omit asset identifiers, so recovery requires authorized
  Cloudinary inventory/database reconciliation rather than retrying from logs.
- Process crashes between upload, save, and deletion can leave orphaned assets.
  Malformed upload results lacking identifiers cannot be safely cleaned up.
- A database write can commit but lose its acknowledgement. Compensation after
  that ambiguous failure could remove a committed replacement. Durable operation
  tracking and reconciliation are needed to resolve this distributed-systems
  limitation; these mocked tests simulate definite failed writes only.
- Concurrent replacements can orphan intermediate uploads. No locking or new
  database schema was introduced.
- Initial-create Cloudinary compensation, explicit record/profile-image deletion
  behavior, delivery privacy, and account-deletion coordination remain separate
  concerns. Local temporary-file cleanup is addressed below.

## Temporary uploads (P1 Issue 8)

Both Multer storage configurations register their generated UUID filenames with
`utils/tempUploadCleanup.js`. Existing size limits (10 MB attachments, 5 MB
profile images), MIME allowlists, field names, and route authentication order are
unchanged. Unauthorized requests never reach Multer. Filenames still preserve
the original extension; originalName metadata is unaffected.

Cloudinary's upload finally block now removes only registered temporary paths.
The request wrapper also removes remaining paths on response finish/close, or
after Multer reports an error. This covers input-validation and owner-record
lookup early exits, Cloudinary failures, database failures, and partial upload
errors. On disconnect during parsing, cleanup waits for the Multer callback to
avoid missing late writes. A disconnected request does not proceed to its
controller after parsing. Multer keeps its own partial-file cleanup as well.

Cleanup uses asynchronous unlink of exact registered files directly under
backend/uploads. It never scans directories, removes directories, trusts a
mutated req.file.path, or invokes Cloudinary deletion. Untracked files, symlinks,
non-files, and a redirected/symlinked upload directory are refused. Missing files
are harmless. Cleanup does not replace the original response or parser error;
failures log only a generic warning. A failed upload-finally removal can retry
when the response completes. Request listeners and tracking are released after
terminal cleanup, including failed removals.

The process must remain alive for asynchronous response-time cleanup. Hard kills,
crashes, a parser that never completes, and persistent permissions/locking errors
can still leave temporary files. There is no background sweep or retry queue;
pre-existing files are deliberately not touched. Operators must review and remove
confirmed stale temporary files manually. This does not protect against a local
attacker able to mutate the application's upload directory during filesystem
operations; that directory must remain writable only by the application account.

Tests use mocked filesystems, Multer, and Cloudinary, covering success, early
responses, database/upload failures, missing files, parser errors, disconnects,
safe targets, restrictions, and auth-before-upload ordering. Browser checks remain
for ordinary attachments/profile images, invalid forms, oversized/unsupported
files, unauthenticated submissions, and cancelled uploads using disposable data.

`node --test backend/tests/*.test.js` uses mocked database and Cloudinary services.
No real assets, records, emails, or environment files are accessed by these tests.
Manual browser review remains for image/document replacement in each module,
preview/download behavior, Notes AI/RAG behavior, edit-without-file behavior, and
server-error display. Use disposable test resources and normal authorized flows.
