# Cloudinary attachments, cleanup and migration

[Project overview](../README.md) | [Account deletion and recovery](SECURITY.md#account-deletion-audit-and-recovery) | [AI document limits](AI.md)

Current policy: new study attachments are authenticated; profile images remain
public; existing legacy study attachments remain public until separately migrated.
This guide preserves recovery procedures from P1 Issues 7, 8 and 10. No live cloud
or database operations are performed by documentation consolidation.

## Cloudinary replacement safety

Historical issue, fixed by P1 Issue 7: Notes, Assignments, Projects, Courses, and Profile updates deleted the
old Cloudinary resource before uploading and saving its replacement. Upload or
database failure could leave an existing record pointing to a deleted file.

Those five handlers now share `utils/saveWithFileReplacement.js`:

1. Existing authentication, input validation, and owner-scoped lookup run first.
2. Upload a new resource using the existing folder and upload restrictions.
3. Validate the returned public ID, resource type, and delivery URL; assign the
   same attachment/profile metadata fields and save the document.
4. Only after save resolves, attempt deletion of the old typed resource.
5. If upload or save fails, restore the attachment in the in-memory document and
   attempt deletion of the new resource when its identity is available. The old
   resource is never deleted on this failure path. Re-throw the original error
   so existing controller response handling remains in place.

No-file updates preserve their original save behavior. Notes still invalidate
attachment RAG fields when replacing the file; content-related AI invalidation
remains unchanged. Later population/response failures never trigger compensation
for an already-saved replacement.

Cleanup checks Cloudinary results: `ok` and `not found` are accepted as idempotent
success; other results and exceptions produce a sanitized warning without
overriding the successful update or the original save failure. Provider error
details are suppressed for replacement cleanup. Authenticated attachment upload/deletion failures also suppress provider details.
Public profile/legacy callers retain their existing error behavior. Local temporary-file removal runs in finally and
cannot mask a successful remote upload or its original error.

Public IDs are paired with exact `image`, `raw`, or `video` resource type and
`upload` or `authenticated` delivery type (missing delivery type is legacy `upload`).
Unknown legacy attachment types are not guessed: deletion is skipped with a
manual-review warning. Legacy profile images may use the existing image-only
fallback. An identical old/new resource identity is never deleted as compensation
or post-save cleanup. Study uploads use autogenerated IDs with overwrite disabled and authenticated
delivery. Profile image policy is unchanged. This supersedes the original P1 Issue 7
statement that overwrite/delivery policy was unchanged.

### Remaining limitations

- Cleanup is best-effort, with no durable queue or automatic retry. A failed old
  deletion leaves an orphan while the new database reference stays valid; failed
  compensation leaves a new orphan while the old reference stays valid. Sanitized
  warnings deliberately omit asset identifiers, so recovery requires authorized
  Cloudinary inventory/database reconciliation rather than retrying from logs.
- Process crashes between upload, save, and deletion can leave orphaned assets.
  Malformed upload results lacking identifiers cannot be safely cleaned up.
- A database write can commit but lose its acknowledgement. Compensation after
  that ambiguous failure could remove a committed replacement. Durable operation
  tracking and reconciliation are needed to resolve this distributed-systems
  limitation; these mocked tests simulate definite failed writes only.
- Concurrent replacements can orphan intermediate uploads. Replacement locking remains absent; the later privacy fix adds delivery-type
  metadata, not a concurrency protocol.
- Initial-create Cloudinary compensation, explicit record/profile-image deletion
  result checking and account-deletion coordination remain separate concerns.
  New-attachment privacy is implemented below; legacy-public migration is pending. Local temporary-file cleanup is addressed below.

### Temporary uploads (P1 Issue 8)

Both Multer storage configurations register their generated UUID filenames with
`utils/tempUploadCleanup.js`. Existing size limits (10 MB attachments, 5 MB
profile images), MIME allowlists, field names, and route authentication order are
unchanged. Unauthorized requests never reach Multer. Filenames still preserve
the original extension; originalName metadata is unaffected.

Cloudinary's upload finally block now removes only registered temporary paths.
The request wrapper also removes remaining paths on response finish/close, or
after Multer reports an error. This covers input-validation and owner-record
lookup early exits, Cloudinary failures, database failures, and partial upload
errors. On disconnect during parsing, cleanup waits for the Multer callback to
avoid missing late writes. A disconnected request does not proceed to its
controller after parsing. Multer keeps its own partial-file cleanup as well.

Cleanup uses asynchronous unlink of exact registered files directly under
backend/uploads. It never scans directories, removes directories, trusts a
mutated req.file.path, or invokes Cloudinary deletion. Untracked files, symlinks,
non-files, and a redirected/symlinked upload directory are refused. Missing files
are harmless. Cleanup does not replace the original response or parser error;
failures log only a generic warning. A failed upload-finally removal can retry
when the response completes. Request listeners and tracking are released after
terminal cleanup, including failed removals.

The process must remain alive for asynchronous response-time cleanup. Hard kills,
crashes, a parser that never completes, and persistent permissions/locking errors
can still leave temporary files. There is no background sweep or retry queue;
pre-existing files are deliberately not touched. Operators must review and remove
confirmed stale temporary files manually. This does not protect against a local
attacker able to mutate the application's upload directory during filesystem
operations; that directory must remain writable only by the application account.

Tests use mocked filesystems, Multer, and Cloudinary, covering success, early
responses, database/upload failures, missing files, parser errors, disconnects,
safe targets, restrictions, and auth-before-upload ordering. Browser checks remain
for ordinary attachments/profile images, invalid forms, oversized/unsupported
files, unauthenticated submissions, and cancelled uploads using disposable data.

`node --test backend/tests/*.test.js` uses mocked database and Cloudinary services.
No real assets, records, emails, or environment files are accessed by these tests.
Manual browser review remains for image/document replacement in each module,
preview/download behavior, Notes AI/RAG behavior, edit-without-file behavior, and
server-error display. Use disposable test resources and normal authorized flows.

## Attachment privacy and legacy migration

### Implemented policy

New Notes, Assignments, Projects and Courses attachments use Cloudinary
`type: authenticated`, with overwrite disabled. Metadata stores `deliveryType`,
`resourceType`, and `publicId`. Only an unsigned, inaccessible Cloudinary URL is
stored/returned for authenticated assets. No signed access URL is sent to browsers.
Profile uploads retain their existing public policy and schema.

Missing deliveryType means **legacy public** (`upload`), including old documents
read through the schema default. The four card components explicitly label these
files `(legacy public)`. They remain publicly accessible to anyone holding their
original URL until a separately authorized migration removes that public copy.
Changing database metadata alone cannot secure a public asset.

### Authorized delivery

Each module provides `GET /api/{note|assignment|project|course}/attachment/:id`.
It requires the existing JWT middleware and valid record ID. The controller
queries `{ _id: recordId, user: authenticatedUserId }`; client IDs never authorize
Cloudinary access. `version=<publicId>` must equal the current attachment's ID.
This is a stale-reference check, not an authorization credential. `download=1`
requests attachment disposition; otherwise safe image/PDF previews are inline.
An owner-scoped recheck after upstream headers rejects deletion or replacement
that happened while connecting. Missing/unowned/stale/cloud-absent files return
404; missing JWT returns 401.

The backend signs a 60-second Cloudinary download URL and fetches it internally.
Legacy files use the stored URL only after HTTPS/cloud-origin validation.
No redirects, upstream cookies, signed URLs, provider bodies or Location headers
are forwarded. Stream pipeline backpressure avoids buffering the whole file on
the server. Limits are 30 seconds total network/stream time and 10 MiB per file,
both declared and actually streamed. Oversized declared responses return 413;
late streaming failures terminate the response because headers may already be
sent. Timeouts before headers return 504; other retrieval failures return 502.

Responses use private/no-store cache control, nosniff, sandbox CSP, safe filename
characters, and an explicit MIME allowlist. Unknown formats and Office documents
download instead of executing inline. Frontend bearer-authenticated Fetch creates
local Blob previews/downloads; it never puts JWTs into URLs. Preview Blob URLs
are revoked when the window closes or after ten minutes, download Blob URLs after
one minute. Popup blocking produces instructions to allow previews or download.
Files are at most 10 MiB but are buffered in browser memory for this JWT flow.

Notes RAG resolves the same authenticated asset metadata server-side, retaining
AI download/text/workload limits and rejecting redirects. Replacement compensation,
old-file deletion, ordinary CRUD deletion, and account deletion use delivery type.
Account deletion resource identity now includes delivery type. Public profiles
and legacy attachments continue using `upload`; authenticated cleanup requests
cache invalidation. Existing replacement commit/compensation ordering and local
temporary-file cleanup are preserved.

### Limits and remaining risks

- Already downloaded files, in-memory previews and streams authorized before a
  deletion cannot be recalled. Every new endpoint request is checked, but there
  is no continuous database permission check during an active stream.
- Backend-only signed URLs remain valid until their expiry. Do not log them or
  include them in telemetry. Network/provider logs require operational review.
- No public assets were migrated, inspected live, deleted or modified by this task.
  Cloudinary account compatibility was confirmed separately by the user (CLOUD-001).
- Legacy URLs must use HTTPS `res.cloudinary.com/<configured-cloud>/...` with no
  query/credentials. Imported custom-CDN or signed legacy URLs require trusted
  review rather than automatic redirects or permissive URL fetching.
- File MIME/extension checking is not a malware scanner. Uploaded documents and
  images should still be treated as untrusted files by users and their viewers.
- Normal CRUD/account deletion retains its existing external-failure/manual-retry
  limitations. No durable cleanup queue or migration executor is added.
- Streaming through Render adds server bandwidth/connections; concurrency and
  account quotas require operational monitoring. Native PDF viewer/mobile behavior,
  real Mongoose serialization and Cloudinary image delivery need browser/integration
  verification. A server-side MIME/CSP header is not carried onto browser Blob URLs;
  the client deliberately restricts inline Blob types to PDF and raster images.

### Migration preparation — DO NOT execute without separate approval

1. **Inventory (read-only, separately authorized):** owner ID, module/record ID,
   public ID, resource/delivery type, format, bytes, stored URL, shared references,
   and Cloudinary asset ID/version. Cross-check resource existence. Exclude public
   profile images. Treat missing delivery type as legacy, not proof of cloud state.
2. **Backup:** encrypted database snapshot/metadata journal plus verified file
   backups or confirmed Cloudinary backup coverage. Restrict backup access; avoid
   adding secrets, URLs or user documents to Git. Record hashes for byte integrity.
3. **Pilot:** use disposable records/assets first. Exercise raw PDF/DOCX/PPTX and
   accepted image formats. Verify unsigned original/transformed access denial,
   owner streaming, cross-owner/unauthenticated denial, RAG and cleanup.
4. **Migration:** prefer copy-and-verify into a fresh authenticated public ID to
   preserve rollback while checking integrity. Journal each step. Use a conditional
   MongoDB update matching the original owner/record/reference so concurrent edits
   are never overwritten. Update delivery metadata and unsigned URL together.
   Reset attachment RAG indexing metadata when public ID changes, following the
   existing replacement invalidation behavior. Keep batches bounded.
5. **Retire public originals:** only after protected access is verified and all
   shared references are accounted for, separately authorize destruction of exact
   old resource/type/ID tuples with cache invalidation. Poll old unsigned URLs and
   relevant derivatives until inaccessible; CDN invalidation is not instantaneous.
   Mark records protected only after public copies are retired and verified.
6. **Retry/recovery:** journal pending-copy, copied, DB-switched, public-retirement
   pending, verified, and failed states. Never infer success from a network timeout.
   Reconcile both MongoDB and Cloudinary before retrying; use exact immutable
   identities and conditional updates. Preserve recovery references on failures.
7. **Rollback:** before public retirement, a conditional DB switch-back can restore
   compatibility but deliberately restores exposure and requires security approval.
   Prefer fixing protected delivery. After public retirement, recover into protected
   storage from backups; do not silently recreate public files. Never bulk-delete a
   folder or roll back unrelated user edits.

### Verification checklist

Automated tests use mocks/isolated memory, never live MongoDB/Cloudinary. Browser
review must cover all four modules, both modes and mobile: create an attachment,
preview/download, expired JWT, another account's record ID, legacy label/access,
replace then retry a previously captured application URL, delete then retry,
Notes document questions, cancelled/broken downloads and popup blocking. Use
disposable accounts/assets only after separately authorizing live operations.

## Isolated authenticated raw-PDF compatibility diagnostic

Historical status at preparation: live compatibility had not been verified.
Subsequently, the user reported CLOUD-001 passed: authenticated raw PDF upload,
unsigned access denial, signed download, byte integrity and cleanup on Cloudinary
Free with PDF/ZIP delivery enabled. This is user-reported evidence, not a live test
performed during consolidation. It does not prove all formats or migration safety.
Existing legacy-public attachments remain public.

### Explicit authorization and execution

Do not run until the account owner explicitly approves this disposable live test.
From the project root, in PowerShell:

```powershell
Set-Location backend
node scripts/cloudinaryPrivacyDiagnostic.js --confirm-cloudinary-test
```

The flag explicitly authorizes one new diagnostic upload, its delivery checks,
and cleanup of that diagnostic asset only. Without the flag (including `--help`),
the script prints instructions and performs no cloud operations or environment
loading. Never paste credentials into the command line.

At authorized runtime only, dotenv loads `backend/.env` quietly, preserving
already-set process environment values. The existing `config/cloudinary.js`
supplies the SDK configuration. No environment file is edited or printed.
Node 18+ with global fetch is required; use the project's current supported Node.
No database or application server is loaded. No new dependency is needed.

### Procedure and expected results

1. Generate a tiny, new PDF containing only a generic diagnostic sentence in a
   fresh OS temporary directory. No existing local study file is used.
2. Print the diagnostic public ID for interruption recovery (not a credential).
3. Upload using `resource_type: raw`, `type: authenticated`, a UUID namespace,
   and `overwrite: false`. Verify returned ID, resource type, and delivery type.
4. Request unsigned authenticated delivery AND the equivalent public upload
   path with no cookies or authorization headers. Both must return 401/403/404.
   Network errors, redirects, and other statuses fail rather than count as denial.
5. Generate a server-side `private_download_url` using the exact raw public ID,
   PDF format, authenticated delivery type, and a 60-second expiry. Retrieve it
   only in memory on the backend and compare every byte with the uploaded PDF.
   URLs, credentials, response bodies, and raw SDK errors are never printed.
6. Destroy only the generated raw/authenticated ID with cache invalidation.
   `ok` or `not found` confirms cleanup; up to three bounded attempts are made.
7. Unlink only the generated local PDF and remove only its now-empty directory.

Exit 0 and `OVERALL PASS` require both compatibility checks and cleanup to succeed.
Exit 1 / `OVERALL FAIL` means a check or cleanup failed; no privacy claims should
be made. The test deliberately does not fall back to public uploads or alternate
providers if authenticated raw delivery fails.

### Cleanup and recovery

Cleanup runs in `finally` after success and handled failures, including ambiguous
upload errors. The cleanup target is the locally generated UUID, never an ID
supplied by Cloudinary, a database record, or a command-line argument. A reported
existing-asset collision skips cloud deletion entirely. Profile images and study
attachments are never referenced.

If cleanup cannot be confirmed, retain the printed diagnostic ID and manually
review ONLY that ID with resource type `raw` and delivery type `authenticated`.
Do not delete similarly named folders, use bulk deletion, or target public assets.
An abrupt process kill, machine crash, or outage can prevent cleanup; there is no
durable retry worker. Retain the ID before starting the upload. Local cleanup
failure reports no sensitive path; look for the fresh `study-cloudinary-diagnostic-`
directory in the OS temporary directory, and inspect before removing anything.

Cloud calls have SDK timeouts (60s upload, 30s per cleanup attempt). Retrieval has
a 15s connection/body deadline, a 64KiB body cap, HTTPS Cloudinary-host checks,
and redirects disabled. Upstream account policies that require redirects will
produce a safe failure requiring investigation, not automatic URL forwarding.

### Offline verification

Run from the repository root:

```powershell
node --test backend/tests/cloudinaryPrivacyDiagnostic.test.js
```

These tests mock the SDK and HTTP responses, using disposable local files only.
They do not load environment configuration or contact Cloudinary. They validate
control flow and cleanup, not account compatibility. Live success also does not
establish expired-link rejection, application ownership authorization, migration
safety, all file-format compatibility, or resistance to every CDN-cache scenario.
